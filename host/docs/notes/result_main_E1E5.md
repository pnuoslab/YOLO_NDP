## 1. 지연시간 — 샘플링 없음(sr=1), 3597프레임

단계 합 = Baseline: `host_pre + infer` / NDP: `target_pre(0xC0 왕복) + io + host_pre + infer`. 논문 표 2와 같은 정의다. 평균 ± 표준편차(초), n=3.

| 입력 | Baseline | NDP q85 | NDP q100 | NDP raw | 가속 q85 / q100 / raw |
|---|---|---|---|---|---|
| 1080p H.264 | 47.02 ± 0.07 | 33.47 ± 0.25 | 36.86 ± 0.09 | 29.63 ± 0.16 | 1.41 / 1.28 / 1.59× |
| 1440p H.264 | 178.12 ± 0.40 | 39.01 ± 0.30 | 42.53 ± 0.07 | 35.17 ± 0.41 | 4.57 / 4.19 / 5.06× |

- Baseline은 화소 수보다 **훨씬 빨리** 느려진다: 화소 1.78배(1080→1440)에 시간 **3.8배**, 화소 4배(1080→4K)에 **8.1배**. 명세 01 H2-3의 "4배가 아니라 8배" 관찰이 그대로 재현됐다.
- NDP는 화소 4배에 1.5배만 늘어난다. target의 sws 축소 + 작은 JPEG 덕분에 host 쪽 일이 해상도와 거의 무관하다.
- wall e2e(하네스 박스 후처리 포함)로 보면 4K 가속은 5.7배(446.1 / 78.4 s)다. **어느 정의를 쓰는지 본문에 반드시 적어야 한다.**

원인은 명세 02 결과 §2-3에서 미리 짚어 둔 것이다. **Baseline은 건너뛴 프레임도 `consume_frame()` 으로 전부 디코딩하는데, 그 시간이 `host_pre` 타이머 밖에 있다.** 그래서 sr=5에서 Baseline의 단계 합에는 디코딩의 1/5만 들어간다. NDP의 `target_pre` 는 target이 전 프레임을 디코딩하는 시간을 그대로 포함하므로, 두 값은 **같은 일을 재지 않는다.**

→ **샘플링 비교에는 단계 합을 쓰면 안 된다.** wall e2e를 쓰거나, `consume_frame()` 을 타이머 안에 넣어 재측정해야 한다(명세 02 결과 §8 결정 항목 2번 — 이제 결정이 필요하다).

|---|---|---|---|---|

| 1080p HEVC | 46.98 | 43.04 | 1.09× | 26.76 |
| 1080p **AV1** | 46.48 | **65.44** | **0.71×** | **49.06** |

- **Baseline은 코덱에 거의 무관하다**(같은 해상도에서 ±2% 이내). 비용 대부분이 디코딩 뒤의 `mat_to_image` 라서다(§3).
- **NDP는 코덱에 민감하다.** target의 AV1 디코딩이 H.264의 약 2.7~2.9배 걸린다. target 보고서(`result_02_target.md` §6-3)가 지적한 대로 AV1은 `libdav1d` 가 선택되고, `thread_count=0` 이 14개 코어 affinity에 수십 스레드를 띄우는 **과구독** 상태다. 이 결과에는 그 영향이 들어 있다.
- **"NDP는 항상 빠르다"고 쓸 수 없다.** 1080p AV1에서는 Baseline보다 느리다.

## 5. 전송량 — NDP가 항상 적게 보내는 것은 아니다

| 4K H.264 | 377.8 MB | 115.0 MB (30%) | 367.9 MB (97%) | 1867.5 MB (494%) |

- NDP 전송량은 **출력이 416×416이라 입력 해상도와 무관하게 거의 일정하다**(q85 115 MB). 그래서 이득은 원본이 클 때만 생긴다.
- 1080p에서 q100·raw, 1080p AV1에서 q85는 **원본보다 더 많이 보낸다.**
- **측정 정합성 확인**: 캐시를 비운 Baseline의 host 블록 읽기 = target `bytes_read` = 원본 파일 크기가 13개 Baseline 조건 **전부에서 일치**한다(표: `summary_E1E5.md` 마지막). 9월 측정의 "Baseline은 캐시에서 읽었다" 문제는 해소됐다.

| 1080p H.264 | 1,614 MB | 764 MB | 445 MB | 3,721 MB |

- 4K에서 Baseline host 4.1 GB → NDP host 0.77 GB. 다만 **target 쪽 0.86 GB를 더하면** 시스템 전체로는 4.1 GB → 1.6 GB다. target 메모리는 이번에 처음 hugepage DMA 버퍼까지 포함해 쟀다(target 보고서 §4의 정정).
- **Baseline RSS가 코덱마다 크게 다르다**(4K: H.264 4.1 GB, HEVC 4.9 GB, AV1 1.3 GB). darknet의 전해상도 버퍼는 코덱과 무관하므로, 이 차이는 **FFmpeg 디코더의 프레임 풀** 때문이다. 명세 01 H7-2에서 "5.7 GB를 '원본 해상도 프레임 버퍼' 탓으로 쓰기 어렵다"고 한 판단이 실측으로 확인됐다.
- raw 모드는 target에 결과 전체(1.87 GB)를 DMA 버퍼로 쥐고 있어 target 메모리가 크다.

## 7. CPU 총량 (host + target)

| 입력 (sr=1) | Baseline host | NDP q85 host + target | 비율 | NDP raw host + target | 비율 |
|---|---|---|---|---|---|
| 1080p H.264 | 348.7 s | 244.3 + 111.1 = 355.4 s | 102% | 39.3 + 107.8 = 147.2 s | 42% |
| 4K H.264 | 781.3 s | 234.0 + 287.4 = 521.4 s | 67% | 39.5 + 285.6 = 325.1 s | 42% |
| 4K AV1 | 922.6 s | 238.6 + 464.7 = 703.3 s | 76% | | |

- ⚠️ **NDP JPEG 모드의 host CPU 약 230초는 부풀려진 값으로 보인다.** host가 하는 일은 416×416 JPEG 복원 + 추론뿐인데, raw 모드(JPEG 복원 없음)는 39초다. 차이는 OpenCV `imdecode`/`cvtColor` 의 작업자 스레드 풀이 병렬 구간 뒤에도 busy-wait 하는 비용으로 보인다(**추정**, 스모크 §4-3에서 처음 관찰). 실제 계산량이 아니라 대기 중 spin이므로, CPU 절감을 논문에 쓰려면 `cv::setNumThreads()` 를 고정해 다시 재거나 이 한계를 명시해야 한다.
- 그 점을 감안해도 **NDP는 CPU를 "없애는" 것이 아니라 target으로 "옮기는" 것**에 가깝다. 1080p에서는 총량이 거의 같고, 4K에서야 줄어든다.

## 8. 전체 측정 전·후 결정이 필요한 점 (E1+E5에서 새로 생긴 것)

1. **샘플링 비교의 지연 정의**(§2). wall e2e로 바꿀지, `consume_frame()` 을 타이머에 넣어 sr>1 조건을 재측정할지. 지금 E2도 같은 정의로 돌고 있다.
2. **AV1 비교의 공정성**(§4). target의 dav1d 과구독을 그대로 둘지(실제 배포 조건), 스레드 수를 affinity 폭(14)에 맞춰 재측정할지.
3. **host CPU의 OpenCV spin**(§7). CPU를 논문 지표로 쓸 계획이면 `setNumThreads` 고정 후 재측정이 필요하다.
4. 전송량 주장 범위(§5) — "NDP는 전송량을 줄인다"는 고해상도·q85에만 성립한다.
