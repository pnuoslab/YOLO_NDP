## 2. §2 코드 수정 요약

커밋 `b99a7b8`, `fb53280`, `fd52c93`.

### 2-1. 타이머가 루프 전체를 덮게 함

e2e 창 안의 모든 구간에 타이머를 붙였다. 남는 것은 타이머 호출 자체와 루프 제어뿐이고, 그 크기가 `resid_pct`다.

| 구간 | 타이머 | 내용 |
|---|---|---|
| e2e 시작 ~ 영상 열기 | `bl_open` | Baseline: `get_capture_video_stream()` + 속성 읽기 |
| 0xC0 / 0xC2 | `target_pre` / `io` | NDP (기존) |
| 그 밖의 루프 전 구간 | `setup` | NDP: 결과 버퍼 할당·memset, 헤더 검사, 프레임 크기 통계 / Baseline: 파일 `stat` |
| 프레임 → 네트워크 입력 | `pre` (`host_pre`) | 기존. Baseline의 sr > 1 건너뛰기 디코딩(`consume_frame`)도 여기에 포함(이전엔 타이머 밖) |
| `network_predict` | `infer` | 기존 |
| `get_network_boxes` + NMS | `post` | **새로 추가.** 성능 실행은 `-post_thresh`(기본 0.25), 정확도 실행(`-labels`·`-dump_dets`·`-save_log`·`-save_img`)은 0.005 |
| 라벨 읽기·mAP 장부·로그·진행 표시 | `eval` | **새로 추가.** 성능 실행에서는 mAP 장부를 건너뜀 |
| 프레임별 해제 | `cleanup` | **새로 추가.** `free_detections`·`free_image`, Baseline 전체 해상도 사본 `release_mat(in_img)` |

- Baseline의 `release_mat(in_img)`는 **원래 위치(프레임 읽은 직후)에서 그대로 해제하고 시간만 cleanup으로 넘긴다.** 처음에는 추론 뒤로 옮겼다가 되돌렸다. 해제 순서가 −6%의 원인은 아니었지만(§3-3), Baseline 경로를 바꾸지 않기 위해서다.
- `get_image_from_stream_letterbox()` 안의 해제(`free_image(tmp)`, `release_mat(src)`)는 기존 하위 타이머(mat2img, decode)에 이미 들어 있다.

### 2-2. 시작 시각 정렬

- **Baseline**: `get_capture_video_stream()` 직전에 e2e를 시작한다. 이전에는 루프 직전이었다.
- **NDP**: FIEMAP + 0xC0 직전에 시작한다(기존과 같음).
- **NDP의 영상 열기**는 e2e 밖에 두고 `ndp_meta_open`(0.12 s)으로 따로 출력한다.
  - 코드상 NDP 경로에서 이 열기는 원본 해상도(`orig_w/h` → `get_network_boxes`의 좌표 복원)와 프레임 수(정렬 검사)에만 쓰인다. 루프에서는 읽지 않는다(`detector.c`의 NDP 분기는 `cap`을 쓰지 않음). 명세의 판단과 맞다.
  - 다만 이 열기가 볼륨에서 **3~5 MB를 읽는다**(§4-F의 `host_block_read`).
- **GPU 워밍업**: e2e 전에 더미 입력으로 `network_predict` 3회를 돌린다(두 파이프라인 동일, `-warmup <n>`으로 변경 가능, 0.06~0.09 s).

### 2-3. host CPU

- 단계별 CPU를 출력한다: `host_cpu_pre/infer/post/eval/cleanup_s`.
- 루프 전체 CPU를 `/proc/self/stat`으로도 읽는다(`host_cpu_procstat_s`).
- **OpenCV 대기 확인**:
  - `ndp_jpeg_to_image()`는 `cv::imdecode` + `cv::cvtColor` + `mat_to_image`다. 이 빌드의 OpenCV 4.6 병렬 프레임워크는 **TBB**다(`cv2.getBuildInformation()`).
  - `-cv_threads 1`(`cv::setNumThreads(1)`, NDP 경로만)을 주면 프로세스 스레드가 259 → 132로 줄고 CPU가 190 → 15.6 s로 준다(§4-D).
  - 줄어든 CPU의 94%(166 s)가 `host_cpu_infer`에서 빠졌다. 즉 추론하는 동안 TBB 작업자들이 기다리며 CPU를 태우고 있었다. raw 모드는 OpenCV를 부르지 않아 처음부터 132스레드·10.5 s다.
  - **원인: OpenCV(TBB) 스레드 풀의 대기 spin — 확정**(스레드 수·CPU 위치·raw 대조로).
- Baseline에는 `-cv_threads`를 적용하지 않는다(Darknet 표준 유지).

### 2-4 ~ 2-6. 하네스 (`run_all.sh`, `collect_row.py`)

- NIC 바이트를 실행 전후로 읽는다(host `enp133s0f0`, target `ens1f0`, target은 관리망 ssh로).
- 감시 프로세스가 1초 간격으로 `Threads`를 표본해 `host_thr_peak`를 남긴다.
- 실행마다 `[cmd]` 전체 명령줄을 로그에 남긴다.
- 파일럿 스텝은 `P3 L1 L2 C1 D1 D1b D2 K1 K2`다.
- `-dec_threads`는 cdw14로 넘긴다. target 필드 `dec_name`, `dec_threads_req/set`, `thr_peak`, `thr_base`가 행에 들어온다.
- 링크 확인:
  - `ip route`에서 <DATA_SUBNET>/30은 `enp133s0f0`에만 붙어 있다.
  - 유휴 10초 동안 rx 360 B, tx 816 B(keep-alive 수준)였다.

### 2-7. 새 `[MEASURE]` 필드

기존 27개 필드 뒤에 붙였다.

| 필드 | 뜻 |
|---|---|
| `post_thresh` | 실제로 쓴 후처리 신뢰도 하한 |
| `cv_threads` | `cv::getNumThreads()`, 손대지 않았으면 −1 |
| `dec_threads_req` | cdw14로 보낸 값 |

### 3-3. 무엇 때문인가 — 원인 미확정

| 가설 | 실험 | 결과 |
|---|---|---|
| 해제 순서(in_img를 추론 뒤로 옮김) | 원래 위치로 되돌림 | 34.0~34.2 — **아님** |

- 비교에 쓴 워크트리는 스크래치패드에 남겨 두었다.

## 6. 본측정 명세(04)에서 바꿔야 할 점

1. **10/19 값과 비교하는 절(§5-2 "10/19 대비")은 e2e로는 의미가 없다.**
   - 10/19 e2e에는 0.005 후처리가 들어 있다.
   - 비교는 `target_pre`, `infer`처럼 정의가 같은 단계만 가능하다. 그것도 host 단계는 빌드에 따라 수 % 움직인다(§3-3).
2. **시작 조건 #2·#5와 블록 F를 고쳐야 한다.**
   - 사용자가 `nvmf_tgt_measure_v2_fix`를 측정 바이너리로 정했다. 명세의 "v2로 재고 v2_fix는 블록 F"라는 구도가 뒤집힌다.
   - v2_fix가 바꾸는 것은 폭이 8의 배수가 아닌 입력의 darknet 조건뿐이다. 이번 입력 12개 중 **MOT20-03(1174)만** 해당한다(`ffprobe`로 확인).
3. **블록 C(코덱)에 AV1 `-dec_threads 6`을 넣을지** 정해야 한다. 14는 libdav1d에서 25스레드가 되어 "14코어에 맞춤"이 아니다. auto(0)는 같은 바이너리로 반드시 같이 잰다(명세에 이미 있음).
4. **host CPU**: 블록 D(`-cv_threads 1`)가 연산 CPU를 재는 유일한 방법이다. 지연은 같으므로, `-cv_threads 1`을 NDP 표준으로 할지도 결정 사항이다(§7).
5. **host 메모리는 VmHWM**을 쓴다. storage 메모리는 JPEG 모드에서 CV가 최대 21%라 그대로 쓰지 않는다(반복 최댓값 등 다른 요약이 필요하거나, 원인을 target에서 조사).
6. **전송량은 "페이로드 + 4.6%"**로 설명된다. NDP의 메타 열기 읽기(3~5 MB)를 표에서 따로 보인다.
7. **4K raw e2e CV 2.2%**가 기준을 살짝 넘는다. 반복 5회를 유지한다(명세 04 블록 A는 이미 5회).
8. **소요 시간 추정**에 쓸 새 값은 다음과 같다.
   - Baseline 4K는 384 s다(10/19는 446 s).
   - darknet 4K는 150~155 s다(03b K1 실측. 1440p는 1080p와 4K 사이로 추정).

## 7. 사용자 결정이 필요한 점

1. **host_pre −6%의 원인을 끝까지 찾을지** — `perf`(sudo) 또는 변경 단위 이분 탐색 약 15~20분. 찾지 않으면 "빌드 간 수 % 차이, 같은 빌드 안에서만 비교"로 적는다.
2. **NDP의 `-cv_threads 1`을 표준 설정으로 할지** — 지연 변화는 CV 범위 안(−1%), host CPU는 190 → 15.6 s. Baseline에는 적용하지 않으므로 "NDP host만 OpenCV 스레드 1"이라는 단서가 붙는다.
3. **디코더 스레드 정책** — target 보고서 §5-2의 (A) 전부 auto / (B) AV1만 제한 / (C) 전부 14코어 맞춤. 이번 데이터는 **제한할수록 느리다**는 쪽이다.
4. **storage 메모리(JPEG 모드)** — 제외할지, 원인(반복마다 21% 흔들림)을 target Claude에게 조사시킬지.
5. **명세 04의 블록 F 처리** — v2_fix가 표준이 됐으므로 블록 F를 빼고 "10/19(수정 전) vs 04(수정 후) MOT20-03 darknet" 비교로 대신할지.
